# 開発運用

正式な規約は [.github/copilot-instructions.md](../.github/copilot-instructions.md)。AGENTS.md と CLAUDE.md は同じ規約を参照する。

開発基準は develop（既定ブランチ）。通常の変更は Issue → 作業ブランチ → 検証 → Draft PR。master はリリース確定版のみで、最初のリリース時に作る。初期シードのみ直接作成する。

Advanced Security、secret scanning、push protection、develop/master/タグの ruleset はユーザーが設定する。既存の保護ルールを自動で緩和しない。CI 名を required checks に登録する場合は、実行済みチェックを GitHub 側で選ぶ。

参照サブモジュールの定期更新は GitHub App を使い、更新 Issue と Draft PR を作る（[reference-submodule-update.yml](../.github/workflows/reference-submodule-update.yml)）。設定名は既存プロジェクトと共通の `MY_REPO_AUTOMATION_BOT_CLIENT_ID`（Actions variable）と `MY_REPO_AUTOMATION_BOT_PRIVATE_KEY`（Actions secret）。このリポジトリへの登録は未確認で、ユーザーが行う。秘密値は読まない。

更新チェックは上流の `main` の先頭と固定コミットを突き合わせる（リリースタグは表示のためだけに使う）。開いている更新 PR があれば、同じ PR へコミットを足してポインタを最新へ進める（更新のたびに別の PR を作らない）。`main` はリリース前の変更を含むため、文書に版を書くときは確認したコミットと `<Version>` を書く。Dependabot の gitsubmodule には置き換えていない（2026-02 にタグの扱いが変わったばかりで、追従ブランチの決め方と未マージ PR の更新の仕方が公式に書かれておらず、動作を手元で確かめられないため）。変更時は更新 PR の CI と、カレンダー画面の DOM・拡張スタイル・Extensions API の互換性を確認してからマージする。自動マージしない。

Issue/PR へ API キー・実運用設定を貼らない。

## CLA の管理

公開リポジトリへの貢献は、取り込む前に CLA への署名を確認します。
現在は AGPL-3.0-or-later 単独で提供しており、CLA の導入は商用ライセンスの提供開始ではありません。
手順は [貢献のしかた](../CONTRIBUTING.md)、条文は [CLA 草案](../CLA.md) を参照してください。
草案を正式に運用する前に、法務の確認が必要です。

管理者は署名 Issue の投稿者と申告した GitHub ログイン名の一致、同意、許諾権限を確認します。
法人の業務としての貢献では、法人用と個人用の同意、法人を代表する権限と対象の貢献者も確認します。
確認後に [.github/cla/signed.yml](../.github/cla/signed.yml) へ
`login`・`signed`（受領日）・`type`（`individual` / `corporate`）・`note` を記録します。
秘密情報や非公開の承認資料は Issue・PR・署名一覧へ載せません。
初期記録はユーザーの指定により、`pmc-ko` の法人署名（2026-10-22）の 1 件のみです。

[CLA Check](../.github/workflows/cla-check.yml) の `cla` は、
PR の作者と **base コミットの署名一覧**を確認し、PR 側のコードを実行しません。
PR 内で署名一覧に自分を追記しても、その PR の判定には使われません。
一覧の変更を対象 base ブランチへ取り込み、PR を更新して再実行します。
未署名の場合は失敗し、同じ案内を重複投稿しないようコメントします。
Dependabot・GitHub Actions・`my-repo-automation-bot[bot]` は成功として報告します。
ただし、署名一覧がない場合は bot も含めて失敗します。

### 導入時の制約

導入 PR の base には署名一覧がないため、PR 自体の `cla` は失敗しうる状態です。
新規ワークフローが base に存在しない段階では、チェック自体が起動しない場合もあります。
この PR では GitHub の設定・ルールセットを変更せず、`cla` の必須化も行いません。
導入 PR をマージし、署名一覧とワークフローを対象 base ブランチへ配置した後、
別作業で実行結果を確認してから `cla` を必須化します。`master` への配置も同様に確認します。

### 法務の確認事項

草案の許諾条項は Template から変更せず、対象ソフトウェア名のみ本製品へ置き換えています。
条文の「当社」は株式会社ビークルビジョンのままです。
現在の製品の名義である株式会社ピー・エム・シー ITソリューション事業部との関係、
正しい許諾先、商用再許諾・特許許諾の範囲、法人と個人の同意記録の十分性を法務へ確認してください。
草案の注意書きは、確認が完了するまで外しません。
